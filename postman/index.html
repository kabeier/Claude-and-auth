Ticked Auth in Postman

Do what the login form will do, by hand: sign up, get a token, then send the same request as a stranger and as a logged-in user. Build it yourself (best for learning), or import the ready-made collection at the bottom.

Build it yourselfSet up, then 5 requests in order. About 15 minutes. Import the ready-made collectionDownload or copy the JSON, then set two variables.

Before you start

  1. Postman is installed and you're signed in (Full-Stack Apps homework, step 1).
  2. Turn off Confirm email: Supabase → Authentication → Sign In / Providers → Email → Confirm email off → Save. With it on, sign-up sends an email and gives you no token.
  3. Your Project URL: Supabase → Integrations → Data API → Project URL. If it ends in /rest/v1/, delete that part.
  4. Your publishable key: Project Settings → API Keys → Publishable key (starts sb_publishable_). Never the secret key.
  5. Using your own app? Everything works the same. Swap tasks for one of your tables, and the body for your columns.

The one picture to keep in mind:

apikey: <publishable key>      → WHICH PROJECT  (never changes)
Authorization: Bearer <...>     → WHICH USER

  Bearer <publishable key>  → role anon           (a stranger)
  Bearer <access_token>     → role authenticated  (logged in)
                              auth.uid() = the token's sub

Build it yourself

1 · Make the collection

  1. Postman → New → Collection. Name it Ticked Auth.
  2. Click the collection, open the Variables tab, and add three rows:
    VariableValue
    base_urlYour Project URL, no /rest/v1 on the end:
    https://your-project-id.supabase.co
    publishable_keyYour publishable key
    access_tokenLeave it empty. Sign up fills it in.
  3. Click Save (top right). Without it, the variables are empty.

Why no /rest/v1? One project URL has two services. /auth/v1/… is Supabase Auth (logins), and /rest/v1/… is your tables. Each request adds its own path.

2 · Sign up and keep the token

POST 1 Sign up

URL
{{base_url}}/auth/v1/signup
Headers
Headers tab → Bulk Edit → paste: 
apikey:{{publishable_key}}
Content-Type:application/json
No Authorization yet: nobody is logged in. That's what this request is for.
Body
Body → raw → JSON: 
{"email": "test@ticked.app", "password": "password123"}
Expect
200 with access_token (the JWT), refresh_token, expires_in: 3600 (1 hour) and user.
Check
Supabase → Authentication → Users: the account is there. That's Supabase Auth's own table, auth.users.

Save the token into the variable. Pick one:

  1. By hand: copy the access_token value from the response (without the quotes). Paste it into the collection's access_token variable. Save. Redo this every time you get a new token.
  2. Automatically: in the request, open Scripts → Post-response (older Postman: Tests) and paste the script below. Send again with a new email, or use 2 Log in. The variable fills itself. 
    const body = pm.response.json();
if (body.access_token) { pm.collectionVariables.set('access_token', body.access_token); }

POST 2 Log in

URL
{{base_url}}/auth/v1/token?grant_type=password
Headers
Same as Sign up. Easiest: right-click 1 Sign up → Duplicate, rename it, change the URL.
Body
The same email and password.
Expect
200 and a new pair of tokens. This is what the Log in button will send. Use it whenever your token expires (after an hour).

3 · Read the token

  1. Paste the access token into the JWT X-ray. Nothing leaves the page.
  2. Find sub (your user id: compare it with Authentication → Users), role (authenticated) and exp (one hour from now).
  3. Anyone can read a token. Nobody can change one: the signature would stop matching.

4 · The same table, as a stranger and as a user

GET 3 GET tasks as anon (a stranger)

URL
{{base_url}}/rest/v1/tasks
Headers
apikey:{{publishable_key}}
Authorization:Bearer {{publishable_key}}
Body
none
Expect
200, every task. Friday's dev rules are to anon, so strangers get in.

GET 4 GET tasks as the logged-in user

URL
{{base_url}}/rest/v1/tasks
Headers
Only the Authorization line changes: 
apikey:{{publishable_key}}
Authorization:Bearer {{access_token}}
Body
none
Expect
200 []. Logged in, and you see less than a stranger. Why? See below.

POST 5 POST a task as the logged-in user

URL
{{base_url}}/rest/v1/tasks
Headers
apikey:{{publishable_key}}
Authorization:Bearer {{access_token}}
Content-Type:application/json
Body
{"title": "Logged-in task"}
Expect
403 "new row violates row-level security policy". Friday's anon POST without a rule got 401. Now Supabase knows who you are, and still says no: authorization.

Why [] on 4 and 403 on 5?

tasks: RLS is ON
  "dev: open access until auth"  to anon           ✅  Friday
  (no policy)                    to authenticated  ❌  ← you
  • Authentication worked. The token is valid, so Supabase knows exactly who you are. But no rule covers authenticated, and RLS's default is no.
  • Reading = a filter. RLS adds a hidden WHERE to the query. No policy → no row can match → 200 []. "Nothing matched" is an answer, not an error.
  • Writing = a gate. A new row must pass the policy's check. No policy → nothing can pass → 403.
  • The fix (Lecture 2): policies to authenticated with auth.uid() = user_id, so each user gets only their own rows.
  • Already did Lecture 2 on your own app? Then 4 gives only your rows, and 5 gives 201.

5 · Break it on purpose

  1. 2 Log in with a wrong password → 400 "Invalid login credentials". Authentication said no.
  2. Change one letter of access_token, then send 4 → 401. The signature no longer matches. Change it back (or log in again).
  3. 1 Sign up again with the same email → an error that the user already exists.

6 · Clean up

  1. Supabase → Authentication → Users → delete test@ticked.app. Lecture 2's trigger only makes a users row for new accounts, so start Lecture 2 with none.

Import the ready-made collection

The same 5 requests, already built, with the script that saves the token. Good as a check against yours, or as a backup.

  1. Get the collection: Download Ticked-Auth.postman_collection.json
    or copy the JSON from the box below.
  2. Postman → Import (top left). Drag the file in, or paste the copied JSON into the box.
  3. Click the new Ticked Auth collection → Variables. Fill in base_url (no /rest/v1 on the end) and publishable_key. Leave access_token empty. Save.
  4. Check the environment dropdown (top right) says No environment. An environment variable with the same name beats the collection's.
  5. Send the requests in their numbered order. 1 Sign up and 2 Log in save the token for you; 3, 4 and 5 use it. Want a different account? Change the email in both bodies.
