Homework Part I: how authentication works

In this order: (1) the How Authentication Works peer quiz on the curriculum's Assignments page, (2) 50 steps of the FreeCodeCamp Python certification. Want more practice? Do steps 1–3 below with your own project.

1 · Turn off email confirmation (development only)

  1. Your Supabase project → Authentication → Sign In / Providers → Email → turn Confirm email off → Save.
  2. Why: with it on, sign-up sends an email and gives you no token, and Supabase's built-in sender only allows a few emails an hour. Real apps keep it on.

2 · Get a token in Postman

  1. Follow Ticked Auth in Postman: build the requests yourself, or download the collection there and Import it. In the collection's Variables, set base_url (no /rest/v1) and publishable_key, the same values as Part I of the full-stack homework. Save.
  2. Send 1 Sign up. You get access_token, refresh_token and expires_in: 3600. A script saves the access token for the next requests.
  3. Supabase → Authentication → Users: your new account is there.

3 · Read it, use it, clean up

  1. Paste the access token into the JWT X-ray. Find sub (your user id), role and exp.
  2. Change a table name in requests 3–5 to one of yours and send them. As the anon key and as the user: what's different, and why? (Hint: who are your RLS rules to?)
  3. Delete the test account in Authentication → Users before Part II.

6 · The Vite + React prompt

  1. Fill in your URL (no /rest/v1) and publishable key, both from front-end/.env:

- Supabase db schema: supabase/schema.sql
- user journey: front-end/app_outline/user_journey.md
- Project API url: https://your-project-id.supabase.co
- Project API Key: your-publishable-key

I would like you to update the functionality for the User Authentication process. Consider the following actions a user can take:

- Register: A brand new user can sign up for our application and interact with our site.
- Log In: A returning user can interact with our site and ONLY their corresponding data
- Log out: A logged in user can end their session and exit our website while removing their credentials from the front-end code.
- User Confirmation: While logged in we need to have a way of confirming who the user is
    - while logged in if the user refreshes the browser, we should be able of leveraging the current credentials to recover the logged in `user` and their corresponding`data`

Each of these actions should be an independent phase. Utilize playwright to ensure completion of each phase prior to moving on to the next one.

Do you have any questions before completing these actions?
  2. Good answers: a Log in page and a Register page; every other page needs a logged-in user. Show the user's name and a Log out button in the header. Keep all Supabase calls in your one service file. Remove any demo or default user id. Never use the secret key.

7 · Prove it with two accounts

  1. cd front-end && npm run dev. Register account A in a normal window and add something.
  2. Register account B in a private window. B must not see A's data.
  3. Refresh A: still logged in. Log out: back to Log in.
  4. Table Editor → users: one row per account (the trigger made them). Your data's user_id matches the right account.
